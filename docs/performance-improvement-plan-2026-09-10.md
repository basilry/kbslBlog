# Lighthouse 개선 계획과 검수 기준

## 기준 결과

2026-09-10 사용자가 제공한 홈페이지 데스크톱 Lighthouse 13.4.1 보고서 기준: 성능 67, 접근성 100, 모범 사례 77, SEO 100. FCP 2.18초, LCP 3.94초, TBT 0ms, CLS 0.0055. 전체 전송량 4,579,525바이트 중 Pretendard 두 요청이 4,116,594바이트다.

보고서의 미사용 JavaScript 431,923바이트 중 301,068바이트는 브라우저 확장 프로그램에서 발생했다. 확장 프로그램 코드, Google 로그인 상태, 네트워크 프록시 가능성을 사이트 코드의 문제와 구분한다. 실제 개선 전후 수치를 확보하지 않고 목표 점수를 달성했다고 보고하지 않는다.

## 병렬 구현

1. **폰트**: next/font와 별도 @font-face의 중복 로딩을 제거한다. 동일한 Pretendard 디자인을 유지하며 글리프 전체 범위를 보존하는 분할 로딩을 검토·구현한다. 특정 글에 등장하는 문자만 남겨 이후 글을 깨뜨리는 최적화는 하지 않는다. 생성 방식과 원본 라이선스를 기록한다.
2. **공통 리소스**: 실제 사용 지점을 확인해 Swiper와 알림 리소스를 필요한 화면으로 옮긴다. Google Analytics 및 이벤트 기능은 유지하면서 초기 화면에 필요 없는 로딩을 지연한다. 홈뿐 아니라 프로젝트 이미지, 알림이 필요한 화면의 동작을 검수한다.
3. **홈 캐시**: 홈의 force-dynamic 설정과 레거시 글 조회를 검토해 정적 생성 또는 ISR을 적용한다. 새 글은 배포 후 보이고, 레거시 조회 실패가 페이지를 깨뜨리지 않아야 한다. 조회수는 기존 별도 클라이언트 집계를 유지하며 사용자별 상태를 HTML 캐시에 포함하지 않는다.

각 작업자는 담당 파일만 변경하며 커밋·푸시·배포하지 않는다. 공유 layout 통합과 최종 저장소 반영은 주 작업자가 맡는다. 글 본문과 메타데이터, 이미지 자산은 성능 개선 대상으로 변경하지 않는다.

## 통합 검수와 배포

- 각 변경의 diff와 데이터·기능 보존 여부를 주 작업자가 직접 검토한다.
- 타입 검사, 기존 테스트, ESLint, 프로덕션 빌드를 실행한다. 실제 캐시 동작이나 분할 폰트의 문자 보존처럼 회귀 위험이 있는 부분만 의미 있는 검증을 추가한다.
- 확장 프로그램 영향을 배제할 수 있는 측정 수단으로 비교한다. 불가능하면 그 한계를 적고 전송량·실제 폰트 요청·응답 헤더·화면 표시를 직접 확인한다.
- 홈, 글 목록과 본문, 프로젝트 상세, 메뉴와 테마, 조회수 표시를 확인한다. 한글·영문·숫자·기호가 정상 표시되는지 확인한다.
- 발행 저장소가 예상 커밋과 일치하고 사용자 변경이 없는지 확인한 뒤 반영한다. 자동 검사 성공과 운영 URL의 최종 동작을 확인한다.
- 최종 결과에는 변경한 내용, 측정 근거, 남은 제약을 기록한다. 개선 전후 조건이 다르면 점수 차이를 직접적인 개선량으로 해석하지 않는다.

## 진행 상태

- 병렬 구현·통합 검수 완료. 운영 배포 및 최종 확인 진행 중.

## 최종 검수 (2026-09-10)

- 프런트엔드 `npm run check`: ESLint 오류 0(기존 경고 11), 타입 검사, 테스트 39개, 프로덕션 빌드 통과.
- 홈 빌드 결과: 정적 생성, Revalidate 5m. 로컬 프로덕션 HTTP 200, `x-nextjs-cache: HIT`, `s-maxage=300` 확인.
- 로컬 홈 브라우저 리소스 목록에서 분할 폰트 14개(70, 71, 75, 78, 82~91)를 관찰했다. 파일 크기 합계 362,208바이트로, 기존 보고서의 두 폰트 전송량 4,116,594바이트 대비 약 91.2% 작다. 이 비교는 폰트 페이로드 규모이며 전체 페이지 전송량이나 로딩 시간 개선율이 아니다. 홈에서 원본 2MB 폰트 요청은 관찰되지 않았다.
- 한글 제목, 홈 목록, 테마 전환, 메뉴, 프로젝트 이미지 슬라이더 초기화 및 확대 모달 표시를 실제 프로덕션 화면에서 확인했다.
- 공식 Lighthouse 13.4.1 CLI를 설치된 Chrome과 Edge의 새 headless 프로필로 시도했으나 브라우저 연결이 ECONNREFUSED로 실패했다. 개선 후 Lighthouse 점수/FCP/LCP는 확보하지 못했으며 점수 상승을 주장하지 않는다.
- Google Analytics 초기 큐와 최초 페이지뷰 1개, 클릭 큐 보존은 실행 검증했다. 외부 gtag는 load/idle 후 로드하며 이후 SPA 주소를 고정하지 않는다.

## 추가 요청: 방문과 글 조회 분리

사용자 확인에 따라 같은 브라우저의 블로그 방문은 한국 날짜별 하루 1회, 글 조회는 매 열람마다 집계한다. 서버의 날짜+방문 UUID 유일키와 별도 열람 요청 ID로 구분했다. 프런트는 Web Locks로 첫 UUID 생성의 탭 경쟁을 막고 네트워크 실패 후에는 동일 요청을 재시도한다.

Worker 타입 검사·테스트 7개·배포 드라이런 통과. 별도 로컬 D1/Worker HTTP 검증에서 같은날 방문 중복 제거, 글 재열람, 동시 요청/재시도, 다른 브라우저, 일반 페이지, 이전 클라이언트, 읽기 전용 API, Origin/봇 거절을 확인했다. 한국 날짜 전환과 기존 데이터 보존은 SQLite/실제 Worker 처리 코드 테스트로 확인했다.

이전 통계는 보존하므로 누적값과 전환 당일 값에는 이전 집계 기준이 섞여 있다. 저장소 삭제·차단·다른 기기의 한계는 [방문 통계 문서](visitor-counter.md)에 기록했다.
